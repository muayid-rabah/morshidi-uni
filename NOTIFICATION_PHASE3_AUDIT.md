# Phase 3 notification delivery audit (2026-10-21)

Starting commit: `6a56c5b0f7986869b1c431c110535a40e90582a0`. Existing untracked `supabase/migrations/20261021110000_fake_university_free_elective_patch.sql` was preserved. No deployed configuration was read or changed, no migration was executed, and no real event was sent.

The authenticated admin endpoint uses Supabase Auth verification and `UNI_ADMIN_USER_IDS`. The SQLite calendar transition and event insertion are one transaction. The Supabase adapter calls the existing transactional `university_set_registration` RPC with a calendar version check and retries conflicts. Both adapters now avoid a new event when already in the requested state. A new transition emits a global event containing the persisted current term, UUID, aggregate version, timestamp and idempotency key. Tests simulate concurrent requests; real PostgreSQL concurrency, grants, and RPC behavior were not tested. The existing RPC itself does not enforce the state-transition check for other direct callers. An already-open no-op does not persist its request key: a retry after a later close can be interpreted as a new open. A database migration for transactional state-transition enforcement and durable no-op command idempotency is required for a complete guarantee across all callers and state changes. No schema changes are included here.

The sender serializes the exact receiver fields, signs the same UTF-8 body with HMAC SHA-256, sends `X-Uni-Signature`, accepts any 2xx, and stores attempt status. A failed attempt is rescheduled with exponential delay up to 60 seconds. HTTP requests use a five-second abort signal. The worker is a timer in the API process and uses the persistent events table when Supabase is selected. It is inactive if URL or secret is missing, when the process is stopped or suspended, and will resume pending records after a restart if the database persists. Multiple instances do not share a delivery claim, so duplicate requests and racing delivery-state updates are possible. Receiver idempotency can mitigate duplicate ingestion but is unverified against the actual database. Delivery errors during batch scanning are now caught without logging secrets.

Important incompatibilities remain: university `student.created` and `registration.audit` events are not accepted by Morshidi's event model and will retry indefinitely; a sufficiently large backlog may delay other events. The sender's registration calendar aggregate version agrees with the receiver's aggregate key, provided both databases have a compatible version history. Receiver timestamp/ID cursor and frontend polling limitations were documented in Morshidi Phase 2. Neither receiver configuration nor end-to-end streaming was verified. Ensure the receiver store is dedicated to this one university: notification tables have no university identifier, and this isolation cannot be established from the repository. Verify old global rows before enabling delivery. No administrator portal control calls the open endpoint; a smallest safe solution is an authorized admin control using the existing endpoint and explicit state/confirmation, designed separately.
