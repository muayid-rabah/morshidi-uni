# Phase 4A - Notification reliability and registration idempotency

Date: 2026-10-21. Starting SHA: `6a56c5b0f7986869b1c431c110535a40e90582a0`. Existing Phase 3 edits and the unrelated untracked `20261021110000_fake_university_free_elective_patch.sql` remain intact. Only this repository was modified.

The worker uses an explicit receiver-compatible allowlist. Unsupported events remain in the events table with `delivery_terminal_reason=unsupported_event`, a terminal timestamp and no delivered timestamp. Malformed payloads use `invalid_event`. HTTP 4xx responses other than 408, 425 and 429 use `http_rejected` and retain the response status; transient statuses and transport errors retry with the existing backoff. A row state-update error is logged without secrets and later rows are attempted. Terminal rows are excluded from further scans. A terminal rejection requires operator review and a deliberate repair/requeue procedure; no automatic replay is assumed. Existing events and registration audit records remain intact.

Both SQLite and the new PostgreSQL RPC maintain a command ledger for transitions and no-ops. The PostgreSQL RPC locks the command key and calendar row, checks stored or legacy results, records no-ops without an event, and atomically records transitions and their event. Different operation types using the same key fail with a conflict. An idempotency key must be supplied and reused by the caller for retry protection; omitted keys remain generated per request. The API uses a new v2 RPC name so a database missing the migration fails rather than silently using the prior behavior. Existing public RPC is also updated in the new migration. The migration has not been executed, and PostgreSQL concurrency, permissions, RLS and RPC functionality are not verified by static tests. No claim is made for previously processed no-ops, which had no durable record.

No production changes were made.
